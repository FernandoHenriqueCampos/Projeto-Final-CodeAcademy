Laravel Docker Runtime Notes
============================

This file explains the runtime part of the Docker setup, assuming you already
know Docker basics and are mainly new to Laravel inside containers.

1. What Stage 2 is for
----------------------

`FROM dunglas/frankenphp:1-php${PHP_VERSION}-alpine AS runtime`

This is the final image that actually runs the app.

FrankenPHP is:
- PHP runtime
- web server integration (built on Caddy)
- a production-friendly alternative to the classic "Nginx + PHP-FPM" split

So instead of running PHP-FPM in one container and a web server in another,
this image can serve the Laravel app directly.


2. Environment defaults
-----------------------

`APP_ENV=production`
- Laravel runs in production mode by default.

`APP_DEBUG=false`
- disables verbose debug output.

`SERVER_NAME=":8000"`
- tells the web server to listen on port 8000.

`PHP_INI_MEMORY_LIMIT=256M`
- used by `docker/php.ini` to set PHP memory limit.

`COMPOSER_ALLOW_SUPERUSER=1`
- avoids Composer warnings when running as root in the container.


3. Installed packages and PHP extensions
----------------------------------------

`apk add --no-cache`
- installs Alpine Linux packages.

Packages:
- `bash`: needed because the entrypoint script uses bash
- `mysql-client`: gives access to `mysqladmin`, used to wait for MySQL
- `tini`: small init process for correct signal handling in containers

`install-php-extensions`
- installs required PHP extensions for Laravel and this app

Extensions here:
- `pdo_mysql`: MySQL database access
- `intl`: localization / string formatting helpers
- `zip`: archive support
- `bcmath`: precise math helpers
- `opcache`: performance
- `pcntl`: process control, sometimes useful for workers/queue handling
- `gd`: image processing
- `redis`: Redis support


4. Application files
--------------------

`WORKDIR /app`
- the Laravel project lives at `/app`.

`COPY --from=vendor /app/vendor ./vendor`
- copies Composer dependencies from stage 1.

`COPY --from=vendor /app ./`
- copies the full app source from stage 1.

Why multi-stage matters here:
- Composer and dependency installation happen earlier
- the final runtime image stays cleaner
- production dependencies are already prepared before boot


5. Files copied from docker/
----------------------------

`COPY docker/entrypoint.sh /usr/local/bin/entrypoint`
- installs a startup script that runs before FrankenPHP starts.

`COPY docker/php.ini /usr/local/etc/php/conf.d/zz-app.ini`
- adds your PHP overrides on top of the base image defaults.

In this repo, `docker/*` currently means:
- `docker/entrypoint.sh`
- `docker/php.ini`


6. Laravel-specific filesystem prep
-----------------------------------

This part is important in Laravel:

`mkdir -p storage/... bootstrap/cache`
- creates directories Laravel expects to write to.

`chown -R www-data:www-data storage bootstrap/cache`
- gives the runtime user ownership of writable directories.

`chmod -R ug+rwX storage bootstrap/cache`
- makes them writable.

Why Laravel needs this:
- logs go into `storage/logs`
- compiled views, sessions, cache files, etc. go into `storage/framework`
- framework cache files live in `bootstrap/cache`

If these permissions are wrong, Laravel often fails with write errors.


7. Port and health check
------------------------

`EXPOSE 8000`
- documents that the container serves traffic on port 8000.

`HEALTHCHECK ... http://127.0.0.1:8000/up`
- Docker checks Laravel's health endpoint.

This works because in `bootstrap/app.php` the health route is configured as:
- `/up`

If `/up` stops responding, Docker marks the container unhealthy.


8. Startup flow
---------------

`ENTRYPOINT ["/sbin/tini", "--", "/usr/local/bin/entrypoint"]`

Boot order is:
1. `tini` starts first
2. it runs `entrypoint.sh`
3. the entrypoint prepares Laravel
4. the entrypoint finally runs the main command

`CMD ["frankenphp", "run", "--config", "/etc/caddy/Caddyfile"]`
- this is the default process that serves the app.

Note:
- there is no custom `Caddyfile` in this repo
- the image's built-in `/etc/caddy/Caddyfile` is being used


9. What docker/entrypoint.sh does
---------------------------------

This file is the Laravel bootstrap logic for container startup.

It does the following:

1. Ensures `.env` exists
- if missing, it copies `.env.example`
- if there is no example file, it creates an empty `.env`

Why this matters:
- Laravel expects environment config to exist
- containers are often started in fresh environments

2. Generates `APP_KEY` if needed
- runs `php artisan key:generate --force`

Why this matters:
- Laravel uses `APP_KEY` for encryption, signed cookies, and related security
- without it, parts of the app will fail

3. Waits for MySQL
- only when `DB_CONNECTION=mysql` and `DB_HOST` is set
- uses `mysqladmin ping`

Why this matters:
- `depends_on` in Compose starts containers in order, but does not guarantee
  the database is ready to accept connections

4. Runs migrations
- controlled by `RUN_MIGRATIONS`
- default is effectively `true`

Command:
- `php artisan migrate --force --no-interaction`

Why `--force`:
- Laravel requires it in production mode

Why `|| true` is there:
- container startup will continue even if migrations fail
- that is convenient in some environments, but it also hides migration errors

5. Handles Laravel caches
- in production:
  - `php artisan config:cache`
  - `php artisan route:cache`
  - `php artisan event:cache`
- outside production:
  - clears config and route caches

Why this matters:
- production cache commands make Laravel boot faster
- development should stay flexible, so caches are usually cleared

6. Creates the public storage symlink
- `php artisan storage:link --force`

Why this matters:
- files stored under `storage/app/public` become available through
  `public/storage`
- common for avatars, uploads, and other user files

7. `exec "$@"`
- replaces the shell script with the final main process
- this is the correct container pattern because signals reach FrankenPHP


10. What docker/php.ini does
----------------------------

This file is not a full PHP config. It is an override file loaded by PHP.

Settings here:
- `memory_limit = ${PHP_INI_MEMORY_LIMIT}`
- `upload_max_filesize = 64M`
- `post_max_size = 64M`
- `max_execution_time = 120`
- `date.timezone = UTC`

These are straightforward runtime limits for the app.

It also enables and tunes OPcache:
- `opcache.enable = 1`
- `opcache.validate_timestamps = 0`
- JIT buffer and JIT mode are enabled

Laravel meaning:
- OPcache improves PHP performance in production
- `validate_timestamps=0` means PHP does not keep checking files for changes
- good for immutable production images
- not good for live code editing inside the container unless you rebuild/restart


11. How this maps to Laravel specifically
-----------------------------------------

The Docker setup is doing four Laravel-specific jobs:

- prepares writable framework directories
- ensures `.env` and `APP_KEY` exist
- optionally runs database migrations on boot
- warms Laravel caches for production

That is the main difference from a more generic PHP container.


12. How it connects to compose.yaml
-----------------------------------

In `compose.yaml`:
- `app` exposes port `8000:8000`
- `DB_HOST=mysql` points Laravel to the MySQL service
- `app_storage:/app/storage` persists Laravel storage across container rebuilds

That last part matters because Laravel writes uploads, logs, and cache files
under `storage/`.


13. Practical mental model
--------------------------

A simple way to think about this image:

- Stage 1 builds PHP dependencies
- Stage 2 is the production Laravel runtime
- `entrypoint.sh` prepares the app every time the container starts
- `php.ini` tunes PHP behavior
- FrankenPHP serves the Laravel app on port 8000


14. One caveat worth knowing
----------------------------

`php artisan migrate --force --no-interaction || true`

This is convenient for local/dev setups, but in stricter production environments
you may want startup to fail if migrations fail, instead of continuing.
